Guía funcional - Permisos de módulo y jerarquía en visitas

Fuente: Notion, página "Jerarquía de permisos a nivel registro". Exportado: 2026-06-18. Módulo: CRM / VISITAS_GESTION.

Objetivo

Esta guía explica, a nivel funcional, cómo se combinan los permisos de módulo configurados en Axapta con la visibilidad por jerarquía y la política de modificación para el módulo web de visitas.

El objetivo es que cualquier persona pueda interpretar la pantalla de configuración de Axapta y entender qué verá el usuario en la aplicación web: qué visitas puede consultar, cuáles quedan en solo lectura y cuándo aparecen los botones de editar o eliminar.

Alcance: este flujo aplica a visitas. Las hojas de gastos mantienen su propio flujo funcional de aprobación, autogestión y estados, por lo que no deben reinterpretarse con estas reglas genéricas de visitas.

Resumen funcional

  • Ver una visita y modificar una visita son dos decisiones separadas.
  • La visibilidad indica qué propietarios o registros puede consultar el usuario.
  • La política de modificación indica si el usuario puede editar o eliminar registros visibles que no son suyos.
  • El comportamiento estándar de la web es restrictivo: si falta propietario, política, permisos del módulo o autorización de jerarquía, el registro se muestra en modo lectura.
  • El propietario funcional de una visita se compara por usuario AX, no por nombre visible ni por alias de CRM.
  • Aunque el módulo tenga Control total, la política de modificación puede impedir editar visitas ajenas.
  • El servidor vuelve a validar antes de guardar o eliminar. La visibilidad de botones en la web es una ayuda visual, no la única barrera de seguridad.

Pantalla de configuración en Axapta

La configuración se gestiona desde Maestro Personas > Accesos Web, dentro del bloque Módulos web.

Cada fila representa los permisos de una persona para una combinación de aplicación web, módulo, empresa, usuario CRM y usuario AX asociado.

Web App

Identifica la aplicación web a la que aplica la regla. Para visitas debe ser CRM. Si una regla se define para otra Web App, no debe esperarse que afecte a visitas del CRM.

ModuleCode

Identifica el módulo funcional. Para el flujo documentado aquí debe ser VISITAS_GESTION. La web no interpreta esta regla por el nombre visible del módulo, sino por el código técnico.

Acceso Módulo

Define el permiso base dentro del módulo.

  • Sin acceso: el usuario no debería operar el módulo.
  • Lectura: el usuario puede consultar si la visibilidad de datos también lo permite, pero no puede editar ni eliminar.
  • Edición: permite que una modificación sea considerada, pero todavía debe pasar la política de modificación a nivel de registro.
  • Control total: permite operaciones completas del módulo, incluida eliminación, pero todavía se somete a la política de modificación y a la jerarquía.
Punto clave: Control total no significa automáticamente poder modificar visitas ajenas. Solo significa que el permiso del módulo no bloquea la operación.

Modo de visibilidad de datos

Define qué registros puede ver el usuario.

  • Solo propios: el usuario ve sus propias visitas.
  • Propios + jerarquía: el usuario ve sus propias visitas y también las visitas de personas que le correspondan por la jerarquía configurada.

La visibilidad sirve para listar y abrir registros. No concede por sí sola permiso para editar visitas ajenas.

Profundidad de jerarquía

Define hasta dónde llega la visibilidad cuando el modo es Propios + jerarquía.

  • Jerarquía directa: el usuario ve sus propios registros y los de subordinados directos.
  • Jerarquía completa: el usuario ve sus propios registros, los de subordinados directos y también los de subordinados indirectos.

Ejemplo: si Marco tiene como subordinada a Amaya y Amaya tiene como subordinado a Alessandro, con Jerarquía completa Marco puede ver visitas de Amaya y también de Alessandro.

Política de modificación

La política de modificación define qué ocurre cuando el usuario abre una visita visible que pertenece a otra persona. Esta es la regla que evita que una jefatura pueda editar todo lo que ve cuando la configuración debe ser solo de consulta.

Solo propios

El usuario solo puede modificar visitas cuyo propietario sea el mismo usuario AX logado.

  • Las visitas propias pueden editarse si el permiso del módulo lo permite.
  • Las visitas de subordinados pueden verse si la visibilidad lo permite.
  • Las visitas de subordinados se abren en modo lectura.
  • En detalle de una visita ajena debe aparecer el campo Propietario.
  • Los botones de editar y eliminar deben estar ocultos para visitas ajenas.
  • Si se intenta guardar o eliminar por una llamada directa, el servidor debe bloquear la operación.

Igual que visibilidad

El usuario puede modificar registros ajenos visibles siempre que la jerarquía devuelva ese propietario como modificable.

  • Las visitas propias pueden modificarse si el permiso del módulo lo permite.
  • Las visitas de subordinados visibles pueden modificarse si el servicio de visibilidad devuelve autorización de modificación para ese propietario.
  • La web puede mostrar editar o eliminar cuando se cumplen permiso de módulo suficiente, propietario visible, política compatible y autorización de modificación activa.
  • Si el propietario no aparece como visible o no aparece como modificable, la visita se muestra en solo lectura.

Reglas del módulo

Esta opción no debe utilizarse como configuración funcional estándar para visitas.

Motivo: genera ambigüedad porque mezcla el permiso general del módulo con la decisión de modificación a nivel de registro. En la práctica puede resultar confuso distinguir si el usuario modifica porque tiene Control total, porque ve el registro por jerarquía o porque existe una regla funcional específica.

  • Mantenerla oculta o desaconsejada en Axapta para visitas.
  • No usarla en nuevas configuraciones operativas.
  • Para visitas, usar preferentemente Solo propios o Igual que visibilidad.
  • La aplicación puede reconocer el valor por compatibilidad técnica, pero la documentación funcional no lo considera una opción recomendada.

Otros campos de la configuración

Resumen de visibilidad

Es un campo de ayuda para explicar la configuración en una sola frase, por ejemplo Propios + jerarquía (Jerarquía completa).

La aplicación web no debe depender de este texto para decidir permisos. La web debe usar los campos estructurados de la configuración y la lista de usuarios visibles que entrega el backend.

Excepciones

Indica si existen ajustes específicos sobre la visibilidad del módulo. Las excepciones pueden agregar o excluir usuarios respecto a la jerarquía normal.

  • Un usuario agregado puede aparecer como visible aunque no venga por la jerarquía base.
  • Un usuario excluido no debe aparecer como visible aunque pertenezca a la jerarquía.
  • Si un registro pertenece a un usuario excluido y se abre por URL directa, debe tratarse como no modificable.
  • Una excepción de visibilidad no debe interpretarse automáticamente como permiso de edición si la política no lo permite.

Usuarios agregados y usuarios excluidos

Estos contadores indican cuántos ajustes manuales tiene la regla del módulo.

  • Usuarios agregados: amplían la lista de propietarios visibles.
  • Usuarios excluidos: reducen la lista de propietarios visibles.

Estos campos afectan principalmente a la visibilidad. La modificación de registros ajenos requiere además una política que lo permita.

Flujo funcional en la aplicación web

1. Inicio de sesión y contexto

Al entrar en la web, el sistema carga el usuario logado, usuario AX asociado, empresa activa, módulos disponibles, permisos por módulo, políticas de visibilidad y políticas de modificación.

Si el usuario no tiene usuario AX asociado o el propietario de la visita no puede resolverse como usuario AX, el sistema debe actuar de forma restrictiva.

2. Listado e historial de visitas

En el historial de visitas, la aplicación obtiene la lista de propietarios visibles para CRM / VISITAS_GESTION.

  • Si el usuario solo puede verse a sí mismo, el historial se filtra por su usuario AX.
  • Si el usuario tiene jerarquía visible, puede aparecer un selector para consultar propietarios visibles.
  • Cuando se selecciona Todos, el backend debe devolver las visitas permitidas por la visibilidad, no todas las visitas de la empresa.
  • Si se selecciona un propietario concreto, se consulta por su usuario AX.

3. Apertura del detalle de una visita

Al abrir una visita, la web identifica el propietario del registro. La comparación se hace contra el usuario AX logado.

  • Si el propietario es el usuario logado, la visita es propia.
  • Si el propietario es distinto, la visita es ajena.
  • Si el propietario no puede identificarse, la visita queda en modo lectura.

4. Campo Propietario en detalle

El campo Propietario aparece cuando se está viendo una visita de otra persona visible.

  • Si no aparece Propietario, normalmente el registro se está viendo como propio.
  • Si aparece Propietario, el usuario está viendo una visita ajena por visibilidad o jerarquía.
  • La aparición del campo no significa permiso de edición. Solo explica la propiedad del registro.

5. Botón editar

El botón de editar debe mostrarse solo si el módulo permite edición, la visita tiene propietario identificable, el servidor confirma que puede modificarse, la política lo permite y, si la visita es ajena, el propietario aparece como visible y modificable.

6. Botón eliminar

El botón de eliminar es más restrictivo que editar. Debe mostrarse solo si el módulo tiene permiso equivalente a Control total o eliminación, la política permite actuar sobre el propietario y el servidor confirma que la visita puede modificarse.

7. Guardado y eliminación

Cuando el usuario guarda o elimina, el backend vuelve a validar permiso del módulo, propietario del registro, política de modificación, visibilidad del propietario y autorización de modificación del propietario visible.

Esto es obligatorio porque la interfaz puede estar desactualizada por caché, recarga parcial o cambios recientes en Axapta. La regla final siempre la impone el servidor.

Combinaciones funcionales habituales

Control total + Propios + jerarquía + Jerarquía completa + Solo propios

Configuración recomendada cuando un jefe necesita consultar la actividad de su equipo, pero no modificarla.

  • Ve sus visitas.
  • Ve visitas de subordinados directos e indirectos.
  • Edita sus propias visitas.
  • Elimina sus propias visitas si el módulo lo permite.
  • Abre visitas ajenas en modo lectura.
  • No ve botones de editar/eliminar en visitas ajenas.

Control total + Propios + jerarquía + Jerarquía completa + Igual que visibilidad

Configuración para jefaturas que pueden gestionar registros visibles de su jerarquía.

  • Ve sus visitas.
  • Ve visitas de subordinados directos e indirectos.
  • Edita sus propias visitas.
  • Puede editar visitas ajenas si el propietario llega como visible y modificable.
  • Puede eliminar visitas ajenas si además el módulo permite eliminación.

Control total + Propios + jerarquía + Solo propios, con visita de subordinado directo

  • La visita aparece en listado si la visibilidad lo permite.
  • El detalle muestra Propietario.
  • El detalle queda en modo lectura.
  • No aparecen botones de editar ni eliminar.

Control total + Propios + jerarquía + Solo propios, con visita de subordinado indirecto

  • Si la profundidad es Jerarquía completa, la visita puede verse.
  • Si la profundidad no incluye indirectos, no debería aparecer en listado.
  • Si se puede ver, sigue en modo lectura porque la política es Solo propios.

Control total + Propios + jerarquía + Igual que visibilidad, con visita de subordinado indirecto

  • Si la profundidad incluye al subordinado indirecto, la visita puede verse.
  • Si el propietario viene marcado como modificable, pueden aparecer botones de editar/eliminar según permiso del módulo.
  • Si el propietario no viene marcado como modificable, queda en solo lectura.

Lectura + cualquier visibilidad + cualquier política

  • El usuario puede consultar lo que la visibilidad permita.
  • No puede editar.
  • No puede eliminar.
  • La política de modificación no debe elevar un permiso de módulo que es solo lectura.

Casos restrictivos

Falta política de modificación

  • El sistema intenta refrescar el contexto de permisos.
  • Si tras refrescar sigue sin política fiable, la web debe actuar en modo restrictivo.
  • En detalle no deben mostrarse botones de modificación para registros ajenos.
  • El servidor debe bloquear operaciones no verificables.

Falta propietario de la visita

  • La visita se muestra en lectura.
  • No se habilita editar/eliminar por jerarquía.
  • Debe revisarse el dato de origen para asegurar que la visita informa correctamente su usuario AX propietario.

Ejemplos prácticos

Ejemplo 1: jefe con Solo propios

  • Configuración: CRM, VISITAS_GESTION, Control total, Propios + jerarquía, Jerarquía completa, Solo propios.
  • El jefe ve sus visitas y las de la jerarquía.
  • Si abre una visita de Estibaliz, Alessandro u otro subordinado, el detalle muestra Propietario.
  • La visita ajena se ve en lectura.
  • No aparecen editar ni eliminar.
  • Si se fuerza una llamada de guardado, el servidor la rechaza.

Ejemplo 2: jefe con Igual que visibilidad

  • Configuración: CRM, VISITAS_GESTION, Control total, Propios + jerarquía, Jerarquía completa, Igual que visibilidad.
  • El jefe ve sus visitas y las de la jerarquía.
  • Si abre una visita ajena visible y modificable, aparecen acciones de edición.
  • Si el propietario visible no viene autorizado para modificación, se muestra lectura.
  • Un subordinado indirecto puede ser editable solo si está dentro de la profundidad de jerarquía y llega como modificable.

Ejemplo 3: jefe con jerarquía completa, pero subordinado excluido

  • El subordinado excluido no debe aparecer como propietario visible.
  • Sus visitas no deben aparecer en la consulta normal.
  • Si una visita se abre por acceso directo, no debe poder modificarse.

Ejemplo 4: usuario sin jerarquía

  • Ve sus propias visitas.
  • No aparece selector funcional de otros propietarios.
  • Edita o elimina solo según su permiso de módulo y la política aplicable.

Cómo interpretar la pantalla de detalle

Veo el campo Propietario

Significa que el registro pertenece a otra persona.

  • Si la política es Solo propios, debe estar en lectura.
  • Si la política es Igual que visibilidad, puede ser editable solo si el propietario llega como modificable.

No veo editar ni eliminar

Puede ser correcto por cualquiera de estas razones:

  • El módulo no tiene permiso de edición o control total.
  • La política es Solo propios y la visita es ajena.
  • El propietario no está dentro de la jerarquía visible.
  • El propietario está excluido por excepción.
  • El propietario visible no viene autorizado para modificación.
  • Falta el propietario AX del registro.
  • Falta o no se pudo cargar la política de modificación.

Veo editar o eliminar

Solo debe ocurrir si se cumplen permiso de módulo, política de modificación y validación del servidor. Si una visita ajena muestra acciones con Solo propios, la configuración o el flujo de datos debe revisarse.

Sale error al guardar aunque vea el botón

El servidor es la fuente final de verdad. Puede ocurrir si la configuración cambió después de renderizar la pantalla, el contexto estaba cacheado, el propietario se resolvió de forma distinta al guardar o la lista de visibles cambió entre la carga y la acción.

Trazabilidad y caché

Para diagnosticar problemas de permisos se deben revisar las trazas de carga de contexto web, módulos por empresa, usuarios visibles, política de modificación, propietario de la visita, validación de modificación y decisiones de interfaz enviadas por la web.

Mensajes o conceptos útiles a buscar:

  • visible-users
  • VISITAS_GESTION
  • MutationPolicy
  • CanMutate
  • ownerAxUserId
  • Record mutation permission
  • Module permission client trace
Regla de caché: si faltan datos críticos de política, el backend debe intentar refrescar el contexto. Si después del refresco siguen faltando datos, la decisión debe ser restrictiva. La caché nunca debe convertir una visita ajena en editable si la política real no lo permite.

Reglas para nuevos módulos

Este enfoque debe ser reutilizable para otros módulos, no exclusivo de visitas.

Para incorporar un nuevo módulo se debe definir:

  • Código de Web App.
  • Código de módulo.
  • Campo propietario del registro expresado como usuario AX.
  • Permisos base del módulo.
  • Modo de visibilidad.
  • Profundidad de jerarquía.
  • Política de modificación.
  • Endpoint o servicio que devuelva propietarios visibles.
  • Indicador de si cada propietario visible es modificable.
  • Validación obligatoria en servidor antes de guardar o eliminar.
Reglas técnicas y funcionales: restrictivo por defecto, no confiar solo en la interfaz, no usar nombres visibles como clave de propiedad, no mezclar hojas de gastos con este flujo, no interpretar Control total como permiso automático sobre registros ajenos y documentar cada política antes de habilitarla.

Glosario

Registro propio

Visita cuyo propietario AX coincide con el usuario AX logado.

Registro ajeno

Visita cuyo propietario AX es distinto al usuario AX logado.

Propietario visible

Usuario propietario que aparece en la lista de visibilidad calculada para el usuario logado.

Propietario modificable

Usuario propietario visible sobre el que la política de modificación permite actuar.

Política restrictiva

Comportamiento por el que la web oculta acciones y el servidor bloquea mutaciones cuando falta información o no hay autorización completa.

Igual que visibilidad

Política en la que la capacidad de modificar registros ajenos sigue la visibilidad y la autorización de modificación devuelta por jerarquía.

Solo propios

Política en la que el usuario puede consultar registros ajenos si la visibilidad lo permite, pero solo puede modificar sus propios registros.

Control total

Permiso base del módulo que habilita acciones completas del módulo, pero no anula la política de modificación a nivel de registro.
